# Technical documentation — Secure-UI Showcase

The record the CRA asks for: what this is, who it is for, what can go wrong,
what standards it is built against, where the SBOM is, and how long it is
supported. Written to be handed over with a release without anyone having to
reconstruct it.

Covers the showcase application in this repository. The component library it
demonstrates is a separate product with its own repository; where a statement
here concerns the library it says so.

Last reviewed: 25 August 2026.

## 1. Product description

A Go web application serving the Secure-UI documentation and live component
demonstrations at secure-ui-web.fly.dev.

| | |
| --- | --- |
| Language and toolchain | Go, floor 1.25.13 (`go.mod`, pinned identically in the Dockerfile and CI) |
| Rendering | `templ` v0.3.1001, compiled to Go; no client-side framework |
| Storage | SQLite via `modernc.org/sqlite` — pure Go, no CGO |
| Sanitisation | `bluemonday` v1.0.27 |
| Passwords | bcrypt via `golang.org/x/crypto` |
| Transport | brotli middleware; CSP with per-response nonces |
| Front end | Secure-UI Web Components v0.4.2, installed from npm and served from `secure-ui-components/dist` |
| Deployment | Multi-stage Docker image on Fly.io, running as an unprivileged user after the entrypoint drops privileges |

The application is a single instance with a local SQLite file. Nothing in it is
designed for horizontal scaling.

## 2. Intended use

To convert visiting developers into adopters of Secure-UI. It is a commercial
product site, not a portfolio piece and not a general-purpose application.

Its accounts exist so that a visitor can exercise the authenticated components —
registration, login, password confirmation, profile — against a real server
rather than a mock. **They are demonstration accounts.** The site is not
intended to hold anything a user would be harmed by losing, and its privacy
surface is deliberately small: an email address, a bcrypt hash, session tokens
and login-attempt records.

Not intended for: storing personal data beyond the above, processing payments,
or serving as a template for a production authentication system without review.

## 3. Risk assessment summary

| Risk | Assessment | Treatment |
| --- | --- | --- |
| Vulnerable Go standard library reachable from the request path | **Was live.** 23 reachable advisories in crypto/tls, net/http, net/url, net/mail, net/textproto below Go 1.25.13 | Build floor raised; Dockerfile pinned to the same patch; `govulncheck` runs in CI so a new advisory fails the build |
| XSS in rendered pages | `templ` escapes by default; user-supplied HTML passes through bluemonday; CSP forbids inline script and uses per-response nonces | Residual risk accepted; no client-side templating exists to bypass it |
| Credential compromise on demo accounts | bcrypt hashes, login-attempt records, server-side sessions | Impact bounded — no real data is held |
| Component library defect reaching adopters | The most serious failure available to this project: a library flaw ships to every adopter's users | Reported and handled under `SECURITY.md`; the library is versioned independently |
| Client-side signing key extraction | **Known and published.** The key is a symmetric secret in page memory; same-page XSS can read it | Documented in the site FAQ and component docs as a design limit, not claimed as cryptographic proof |
| Telemetry signal spoofing | **Known and published.** All signals are heuristic | Stated on the site; the value claimed is raising the cost of scripted attacks, nothing stronger |
| Test coverage | **Open.** 10.2% of `internal/`, from three tests in one file | Reported on every CI run; see §7 |

## 4. Standards and frameworks applied

- OWASP Top 10 (2021) — the site publishes its own A01–A10 mapping, with an
  explicit *Addressed* versus *Complementary* distinction. That distinction is
  deliberate and must not be softened: client-side controls complement
  server-side ones and do not replace them.
- WCAG 2.2 AA as the accessibility floor.
- WHATWG HTML, W3C CSS and TC39 ECMAScript as the specifications of record for
  the component library.
- CycloneDX 1.6 for the SBOM.
- EU Cyber Resilience Act — this document, `SECURITY.md`, the SBOM and the CI
  vulnerability gate are the Annex-shaped artifacts.

## 5. SBOM

`sbom.json` at the repository root. CycloneDX 1.6, generated by
`cyclonedx-gomod` v1.9.0 under the deployed target's build constraints
(`CGO_ENABLED=0 GOOS=linux GOARCH=amd64`), because Go's module selection depends
on them and an SBOM built for another target is not an SBOM of the shipped
container.

Regenerate with:

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
  cyclonedx-gomod app -json -output sbom.json -main cmd/server .
```

CI regenerates it on every run and fails if the committed file differs, so it
cannot go stale unnoticed. It covers the Go application only; the npm component
dependency is recorded here and in `package-lock.json`.

## 6. Vulnerability handling

`SECURITY.md` carries the reporting contact and the response windows —
acknowledgement in 3 working days, first assessment in 10, fix or documented
mitigation for high and critical within 30 days of assessment.

An actively exploited vulnerability in a shipped product starts a 24-hour ENISA
early-warning clock at discovery, not at triage.

## 7. Support lifecycle

Supported until **25 August 2031**, five years from this review.

The showcase site is a single deployment; only what is live is supported. The
component library supports its current minor release; it is pre-1.0 and adopters
should track the current version.

Sunsetting is a decision to record here, not something to let lapse quietly.

## 8. Open items against this document

1. **Test coverage is 10.2%.** Three tests over the registration handler, and
   nothing over middleware, session handling, or the security headers. CI
   reports the number but does not gate on it, because a floor set to today's
   figure would ratify it. Set a floor once the handler and middleware paths are
   covered.
2. **The npm component dependency is outside the SBOM.** `cyclonedx-gomod`
   describes the Go module graph only. Either generate a second document with
   `cdxgen` and reference it here, or state the boundary as intentional.
3. **No recorded threat model for the library itself.** The site's OWASP mapping
   describes coverage, which is not the same thing.
